# `add_rms_norm_bias` 优化报告检视意见

## 1. 总体评价

这份报告已经具备较强的工程复盘价值。最突出的优点不是最终性能数字本身，而是形成了较完整的证据链：

- 先通过 tiling 日志确认真实分发变体，避免优化错误路径；
- 按轮次记录瓶颈、改动、性能结果和正确性结果；
- 使用未修改路径估计测试噪声；
- 保留 Reduce 依赖链重构的负结果和回退原因；
- 主动暴露宽松断言导致的假阳性，并补充严格测试；
- 对 UB 超限、数值溢出域和 c220 硬件行为都有实证记录。

当前主要短板不是技术内容不足，而是部分数字口径、复现信息和最终结论的组织方式还可以加强。建议按以下优先级修改。

---

## 2. P0：建议优先修正的准确性与口径问题

### 2.1 核对带宽、搬运量与理论地板

报告当前给出：

```text
搬运 117MB，墙钟 89.4µs，有效带宽约 1.36TB/s，约为峰值的 85%，理论地板约 73µs
```

如果按照十进制单位计算：

```text
117 MB / 89.4µs ≈ 1.31 TB/s
```

需要统一说明：

- 117 的单位是 MB 还是 MiB；
- 带宽使用 TB/s 还是 TiB/s；
- 1.36TB/s 对应的是 89.4µs、86.4µs，还是另一组测量；
- 峰值带宽采用的具体数值及来源；
- 73µs 理论地板的计算公式。

建议在正文中直接写出：

```text
总搬运量 = 元素数 × 每元素有效读写字节数 + 参数张量搬运量
有效带宽 = 总搬运量 / 实测墙钟
理论地板 = 总搬运量 / 目标设备可用峰值带宽
```

### 2.2 澄清“15 遍全宽 pass”与编号 1—17

4.1 节称基线为“每行 15 遍全宽 pass”，但后面的步骤编号到 17。需要明确：

- 哪些是全宽向量遍历；
- 哪些是单元素向量/标量操作；
- 哪些只是同步步骤而不计入 pass；
- 15→12 的具体三项削减分别是什么。

建议改成按类别计数：

| 指标 | 基线 | 第一轮后 | 变化 |
|---|---:|---:|---:|
| 全宽向量遍历 | 待核对 | 待核对 | -3 |
| 单元素向量操作 | 待补充 | 待补充 | — |
| V/S 跨流水同步 | 2 次/行 | 0 | -2 次/行 |
| GM 读写量 | 待补充 | 待补充 | 不变 |

### 2.3 解释性能计数器不能直接相加

`vec busy=73%`、`scalar_wait=85%`、`MTE2/MTE3 busy` 属于可能重叠的流水统计，建议明确注明：

> 各 pipe 指标在时间上可能重叠，不是互斥占比，不能直接相加得到 100%。

### 2.4 收紧“MTE2/MTE3 全部隐藏”的表述

建议改成：

> MTE2/MTE3 搬运大部分与向量计算重叠，未单独落入最终关键路径。

这样可以避免被理解为搬运成本已经消失。

## 4. P2：建议改善的表达与可维护性

### 4.1 分开呈现 decode 与 prefill

1—4 token 与 512—4096 token 的量级和优化机制差异较大。建议：

- decode 单独展示绝对时延和 SINGLE_N 改进；
- prefill 单独展示吞吐、有效带宽和 NORMAL/MULTI_N 改进；
- 避免在同一线性纵轴上让小 token 数据挤在底部。

### 4.2 给伪代码补充代码定位

关键变化旁建议补充：

- 文件路径；
- 类名/函数名；
- 对应 commit；
- 如条件允许，附精简 diff 或伪代码前后对比。

### 4.3 固化负结果模板

建议将 4.6 节整理为固定格式：

1. 假设；
2. 实验变量；
3. 控制变量；
4. 设备观测；
5. 性能与正确性结果；
6. 结论；
7. 是否回退及原因。

### 4.4 增加维护红线

建议在结尾新增“实现约束与维护注意事项”：

- 事件发射条件必须与消费条件一致；
- 事件必须成对分配、等待和释放；
- 双缓冲槽位必须使用局部行号；
- kernel 退出时不得遗留在途事件；
- UB 预算必须由 host tiling 成本模型计算；
- 新 shape 进入 NORMAL 前必须经过严格用例；
- c220 实证行为不能直接外推到其他架构；
- 修改 rstd 压缩逻辑必须覆盖 rows>8 和尾块场景。
