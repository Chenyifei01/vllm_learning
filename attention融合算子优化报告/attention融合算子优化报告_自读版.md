# Attention 融合算子 Ascend 性能优化分享讲稿

> 使用方式：按原 PPT 的 24 页顺序讲述。每页标题用于翻页定位，标题下的正文均可直接朗读；建议分享约 30 分钟。正文到第 24 页结束，后面的问答供交流时使用。

## 第 1 页 开场与优化目标

大家好，今天和大家分享一个 Attention 融合算子在 Ascend 上的性能优化过程。Attention 中文叫注意力，可以先把它理解为：让一个图像区域根据关联程度，从其他区域聚合信息。后面我会结合模型流程，把这个计算讲清楚。

这个算子叫 attn_rel_h_rel_w，来自 DeepSeek-OCR 的视觉编码器。它除了完成普通注意力计算，还会加入图像的二维相对位置偏置。我们这次关注的是这个算子内部的数据流、向量指令和流水调度，不是重新设计整个模型。

先看结果：三个测试场景最终分别达到约 2.74 倍、5.24 倍和 8.75 倍的单算子加速。不过，比记住这三个数字更重要的是理解优化的过程：原来慢在哪里，我们根据什么证据决定怎么改，以及改完之后怎样判断收益。下面就沿着这条线展开。

## 第 2 页 分享结构

今天分三部分。先把算子在模型中的位置和硬件数据流讲清楚；再按实际优化顺序，介绍从冗余指令到流水调度的改进；最后结合性能数据，复盘哪些诊断方法值得复用。

## 第 3 页 测试环境与输入输出

先看测试环境。这次设备是 Ascend950DT_9592，软件使用 CANN 9.1.0 和 tilelang-deepseek。CANN 是 Ascend 的计算软件栈；这里的 TileLang 是描述算子计算和数据搬运的一种编程方式，编译后会生成实际执行代码。后面所有性能数字，都放在这套环境里比较。

接着看三个测试 shape。shape 就是张量各个维度的大小。这三个场景的 batch，也就是一次处理的样本数，分别是 2、1、1；side 分别是 14、40 和 64。这里的 side 是视觉特征网格的边长，不是原始图像的像素宽度。网格展平后，序列长度 S 就是 side 的平方，分别为 196、1600 和 4096。

输入和输出采用 BSHD 布局，这四个字母分别表示批次、序列位置、注意力头和每个头的特征维度。测试里有 12 个头，每个头的维度 D 是 64。多头的意思是，让不同组特征分别学习不同的关联方式。

输入主要使用 BF16，可以理解为占两个字节的浮点格式；累加使用 FP32，也就是四字节浮点格式，用来降低中间计算的数值误差。后面的概率块会转回 BF16。

还有一个后面会反复用到的数字：每次处理 128 个 key，也就是 128 个被关注的位置。不能整除时，最后一个块处理剩余位置，所以三个序列分别需要 2、13 和 32 个 key 块。后面选择 softmax 实现和流水深度，都会用到这个块数。

这些维度现在看起来可能有点抽象。下一页我们把它们放回模型流程，看看这些输入究竟代表什么。

## 第 4 页 模型位置与注意力计算

先看下面的模型流程：文档图像经过 patch embedding，再经过多层 ViT block，得到视觉特征，供后续语言模型使用。

patch 是图像中的一小块，embedding 是把输入转换成向量表示。合起来，patch embedding 就是：把图像划分成小块，再通过可学习的映射，把每一块的像素信息转换成一个特征向量。可以把它想成给每个图像区域制作一张“特征卡片”：原来是一块像素，转换后是一组能够被后续网络处理的数字。这就叫把图像块嵌入到特征空间。这里说的图像块大小，和上一页特征网格的 side 不是同一个概念。

这个向量也叫视觉 token。语言模型里的 token 常常对应一段文字；视觉 token 对应的是一个图像区域，不能直接理解成一个字符，也不等于已经识别出的文字。

ViT 是 Vision Transformer，也就是视觉 Transformer。block 指其中反复堆叠的一个编码层。一个典型的 block 包括注意力、前馈网络、归一化和残差连接。注意力让不同图像区域交换信息；前馈网络，也叫 MLP，对每个位置的特征继续加工；归一化调整数值尺度；残差连接把输入加回输出，让信息能够跨层传递。图里的“乘 N”表示把这样的编码层堆叠多次，每一层继续加工上一层的特征，不表示所有层共用一套权重。

所以，从整个模型看，patch embedding 负责形成最初的视觉特征，ViT block 负责继续理解这些特征。我们这次优化的范围更小，是 block 里面的注意力计算核心，不包括整个 block，也不包括前面生成 Q、K、V 的投影计算。

再看上面的公式。Q、K、V 分别是 query、key、value，可以用“我想找什么”“我能与什么匹配”“我实际携带什么信息”来帮助理解。它们由特征经过不同映射得到，在这个算子里已经是准备好的输入。对一个位置 i，用它的 Q 和其他位置的 K 做点积。点积就是把两组向量对应的元素相乘，再把结果加起来，用这个数表示关联程度。随后除以根号 D，控制分数的尺度。

图像还有二维空间关系，所以这里加上 REL_H 和 REL_W 两项偏置。key 的序号 j 对 side 做整除，结果对应网格行号；再取余数，就得到列号。算子据此取出行和列的偏置，加到分数中，让注意力不仅考虑内容，也考虑空间关系。两张表还与当前 query 和注意力头有关，并不是给所有 query 加同一个位置值。

接着做 softmax。它先通过指数运算把分数变成正数，再做归一化，得到一组总和为一的权重。可以把它理解为给其他位置分配“关注比例”：分数较高的位置分到较大的权重。最后，用这些权重对 V 加权求和，就得到当前位置融合其他区域信息后的输出。这里的 online softmax 是按 key 块逐步更新行最大值、归一化分母和输出累加值。它仍然对应整行的归一化，不是每个块各自归一化后直接拼起来。

最后看硬件分工。Cube 是矩阵计算单元，负责 Q 乘 K 的转置，以及概率 P 乘 V；Vector 是向量计算单元，负责缩放、位置偏置、softmax 和输出重缩放。在这个实现中，AIC 是执行矩阵计算的核，AIV 是执行向量计算的核，一个 AIC 和两个 AIV 协作处理任务。

也就是说，同一份中间数据，要在矩阵计算和向量计算之间来回交接。下一页就看，这个交接实际是怎么完成的。

## 第 5 页 片上数据流与计算交接

这张图描述数据实际怎么走。GM 是全局内存，可以理解为容量较大的外部存储；L1 是这里供矩阵计算使用的片上缓冲；UB 是向量计算使用的片上缓冲；L0C 则用于承接 Cube 的矩阵乘累加结果。它们不是可以随意互换的空间，数据要按执行单元和接口要求搬运。

一个任务开始后，Q 放到 L1，两张位置偏置表放到 UB，在后面的 key 循环中重复使用。K 和 V 则按块从 GM 流入 L1。

Cube 先做 Q 乘 K 的转置，这类矩阵乘在性能分析里也常叫 GEMM。算完以后，把结果交给两路 AIV。AIV 完成缩放、偏置和 softmax，再把概率块送回 Cube，执行 P 乘 V。最后 AIV 更新输出累加值，完成归一化并写回 GM。

为什么还需要 rescale，也就是重缩放？因为在线 softmax 每处理一个新块，行最大值可能改变。旧的分母和输出累加值必须一起调整到新的数值尺度，才能和新块的结果正确合并。

这个分块流程不把完整的 S 乘 S 概率矩阵写回 GM，而是在片上生成一块、消费一块。这是 FlashAttention 类方法的重要思路：减少大中间矩阵的存储和搬运，并不是把注意力改成某种近似算法。

所以这里不仅要让 Cube 或 Vector 各自算得快，还要让它们的数据交接顺畅。否则，一个单元完成了自己的工作，却仍然要等另一个单元。

理解了这个数据流，再去看代码和性能时间线，我们就知道要重点观察哪些交接位置。

## 第 6 页 进入优化过程

有了模型和数据流的背景，下面进入优化过程。我们先看原始实现和性能证据，再看为什么要按这个顺序修改。

## 第 7 页 原始实现的串行结构

这一页是原始实现的伪代码。我们先从外层看起：Persistent 表示工作单元持续领取并处理任务。每个任务开始时，先准备 Q 和偏置表，再进入 key 块循环，逐块处理 K 和 V。

最值得注意的是 T.serial。每个 key 块依次经历 K 和 V 搬运、QK 矩阵乘、偏置和 softmax、概率布局转换、P 乘 V，以及输出更新。一个块处理完，才开始推进下一个块。

这些步骤里确实有不能打破的依赖，比如没有 QK 的分数，就不能计算 softmax；没有概率，就不能做 P 乘 V。但不同块之间，一部分搬运可以与当前块的计算重叠。

原始结构把这些可重叠的工作也排成了队。后面的流水优化就是在保证依赖和同步正确的前提下，让“下一个块的准备”和“当前块的计算”同时推进。

不过，看到串行循环还不能直接认定它就是最大的瓶颈。我们先看测量结果，再决定从哪里下手。

## 第 8 页 初始性能与指令开销

原始实现的三个耗时分别是 33.2、469.2 和 2514.7 微秒。随着序列变长，重复处理的 key 块增加，原有开销也被放大。

Profile 就是性能采样和分析。图里可以看到，AIV 的向量忙碌比例比较高，而 Cube 的矩阵计算占比相对低。但“向量一直在忙”不等于“向量一直在做有效工作”，它也可能忙于重复索引和布局整理。

进一步看 S 等于 4096 时的生成代码，每个 key 块、每路 AIV 对应大约 4294 条 SIMD 指令。SIMD 的意思是，一条指令同时处理多个数据元素。这里，位置偏置相关操作占 2438 条，softmax 占 1344 条，ND 到 NZ 转换占 128 条，输出重缩放占 384 条。

这里要把两个口径分开：忙碌比例来自运行时采样，指令条数来自生成代码。前者告诉我们向量侧很忙，后者帮助我们拆开看它到底忙在什么操作上。

这两个证据结合起来，给出的第一条线索就是：先检查向量侧有没有可消除的重复工作。接下来我们回到生成代码，把这个问题落实到具体操作。

## 第 9 页 从生成代码确认问题

这一页把问题进一步落实到了编译后的代码。高层代码看起来短，不代表生成的指令就少，所以我们用 get_kernel_source 查看实际生成内容。

第一，偏置计算里有一部分索引只依赖 key，却放在了 query 行循环里，导致重复执行。第二，在 side 等于 64 的特殊形状下，仍然使用通用 gather 查表，没有利用连续访问和广播。第三，softmax 先产出普通布局的概率，再额外整理成 Cube 要消费的 NZ 布局。

这三项都可以通过改变指令组织方式减少开销，而不需要改变注意力的数学含义。第一轮我们先处理这些局部开销，再看整体流水还有多少空间。

先看第一项：为什么一个只依赖 key 的索引，会被重复算这么多遍？

## 第 10 页 将 key 相关索引移出 query 循环

先看左边的原始结构：外层遍历 query 行，内层遍历 key 的向量片段。每换一行 query，都重新计算 key 对应的二维位置索引。

但 key 在第几行、第几列，只由 key 的编号决定，和当前是哪一行 query 无关。这就像给同一批地址查邮编，不需要每服务一个客户，就把所有地址重新查一遍。

右边把循环顺序调整过来，先计算 key 相关索引，再在内层遍历 query 行。真正依赖 query 的偏置表取值仍然保留在相应循环中，并没有把所有偏置数据都当成常量。

这里有 9 条相关索引指令、64 行 query 和两个向量片段。原来执行 9 乘 64 乘 2，也就是 1152 条；调整后变成 9 乘 2，也就是 18 条。

这里的 1152 到 18，只统计每个 key 块、每路 AIV 的这一组索引指令，不是整个算子的指令数。它体现的是一个很通用的方法：先判断一个表达式依赖哪些变量，再把不随内层循环变化的计算移出去，这就叫循环不变量外提。

重复计算去掉以后，还可以继续问：这些索引所指向的数据，真的需要逐个查表吗？这就进入下一项优化。

## 第 11 页 用广播和连续读取替代特定 gather

第二项优化利用 side 等于 64 的数据规律。gather 是“每个向量位置按自己的索引取一个数”，比较灵活，但会增加地址和取数操作。广播则是把同一个数分发到多个位置；连续读取是按连续地址取一段数据。

可以把向量里的 lane 理解成同时处理的一个数据位置。这里一个向量覆盖 64 个位置。当网格一行也正好是 64 个位置，并满足起始位置对齐条件时，这一段 key 的行号相同，列号连续。

因此，REL_H 可以取一个值广播给整段；REL_W 可以直接连续读取，不必分别按索引查找。代码里的 BRC_B16 和 UNPK_B16 对应这里使用的广播和读取处理方式。

但 side 等于 40 时，一段 64 个 key 可能跨过网格行边界。前 40 个和后面一部分 key 已经属于不同的行，不能套用“整段行号相同”的假设。所以这个场景仍然需要通用 gather 和相应掩码。

因此，我们只在访问规律满足条件时使用广播和连续读取，其他 shape 仍然保留通用 gather 路径。这里节省的是不必要的索引访问，不是牺牲 shape 的正确性。

偏置计算处理完以后，再看 softmax 输出的概率。它在交给 Cube 之前，还有一次布局整理，这一步也值得检查。

## 第 12 页 softmax 直接生成 NZ 概率块

第三项优化涉及数据布局。ND 在这里可以理解为普通的二维逻辑排列；NZ 是一种分块组织的数据排列，更适合这条 Cube 矩阵乘路径使用。它们表达的还是同一组概率值，只是存放顺序不同。

原来 softmax 先把概率写成普通布局，再用一段独立操作整理成 NZ。相当于先按一种规则装箱，下一道工序又把箱子打开、重新装一遍。

优化后，softmax 在产出概率时，就直接写成后续 P 乘 V 所需要的 NZ 布局。这样消除了每个块、每路 AIV 对应的 128 条布局整理指令，以及 16 KB 的中间暂存需求。

这一页代码里的 vcvt 负责把数值转换成 BF16；低半部分和高半部分的位段合并后，再按 NZ 所需位置写入。这里的 vor 是按位合并，不是在做数值相加；reinterpret 也只是重新解释位表示，不是又进行一次数值转换。

还有一点不能忽略：写完概率后，需要保证后续读取能看到这些写入，代码里的屏障正是为这个依赖服务。我们减少的是重复转换和暂存，不是把必要同步删掉。

所以，这一项的思路是：既然后面的矩阵乘需要 NZ，就让前面的 softmax 直接产出 NZ，避免多做一次整理。

但直接输出新布局，不代表在所有场景下都一定更快。下一页我们看它自身的成本，以及为什么短序列没有统一切到这条路径。

## 第 13 页 按序列长度选择 softmax 路径

直接生成 NZ 很有价值，但这个 compact 实现也有额外成本。这里的 compact 指紧凑的布局和处理方式，不是把概率做有损压缩。两条路径的概率都使用 BF16。

这个实现要先求行最大值，再处理指数、写入概率和累计归一化信息，存在两遍处理的成本。对只有两个 key 块的短序列，这些成本不一定划算；对需要反复处理很多块的长序列，减少布局转换的收益更容易覆盖它。

因此，测试中保留了按块数分派的策略：S 等于 196 使用普通路径，S 等于 1600 和 4096 使用 compact 路径，分派阈值是 key 块数至少为 13。

这个阈值是针对当前设备和这几个 shape 调出来的，换场景后还要重新测。我们最终保留了两条路径，让短序列避免额外处理成本，让较长序列获得布局优化的收益。

到这里，第一轮主要改动就讲完了。下面看这些改动合在一起，实际带来了多少收益。

## 第 14 页 第一轮优化结果

第一轮组合了索引外提、特定 shape 的访问优化、概率布局优化，以及基础流水调整。三个场景的耗时变为 14.1、103.3 和 346.7 微秒，相对原始实现分别加速约 2.35 倍、4.54 倍和 7.25 倍。

这说明生成代码里发现的开销，确实值得处理。但这张表是组合优化的结果，不能把全部收益单独算到某一条修改上。

还有一个值得注意的现象：向量忙碌比例下降了，同时总耗时也下降了。这并不矛盾，因为我们删掉了本来就不应该重复执行的工作。

不过，此时长序列仍有明显优化空间。第一轮解决的是“每个块做了多少多余工作”，下面要继续解决“多个块如何交错执行”。

## 第 15 页 第二轮关注计算与搬运交接

第一轮之后，再看两级流水的性能采样。Vector 的计算仍然比较忙，Cube、搬运和结果传输也各有自己的活动区间。

图里的 MTE 是专门的数据搬运引擎，MTE1、MTE2、MTE3 对应不同搬运路径。FIXP 是 Cube 结果输出相关的处理管线，Scalar 则负责标量控制等工作。在时间线上，它们各有自己的轨道，部分工作能够同时推进。

这些比例不能单独证明某条管线是瓶颈，更不能直接相加当成总耗时分解。我们需要结合时间线，看哪些阶段在等数据、哪些地方出现空白。

这轮的优化假设是：给流水多留一个可在途的 key 块，让搬运和计算更充分重叠，从而缩短单元之间的等待。下面用同一实现的两级、三级对比来验证。

## 第 16 页 按块数选择两级或三级流水

这里的流水深度，是允许同时处于不同处理阶段的 key 块和缓冲槽数量。它不是 ViT 的网络层数，也不是注意力头数量。

可以把它理解为一道流水作业：当前块在计算，下一个块在准备；增加一级后，还可以让更多后续准备工作提前推进。但多一级也意味着更多缓冲空间和更复杂的依赖管理，并不是级数越多越好。

本次采用的策略是：key 块数至少为 13 时使用三级，否则使用两级。短序列从一级变两级，耗时由 14.1 降到 13.3 微秒；中等序列从两级变三级，由 103.3 降到 89.5 微秒；长序列由 346.7 降到 287.9 微秒。

对应的时延下降大约是 5.7%、13.4% 和 17.0%。这里说的是相对上一轮的时延降幅，不是相对原始实现的累计加速倍数。

从结果看，中长序列确实受益于更深的流水；短序列也有改善，但适合的是两级。这说明流水深度要结合块数、缓冲成本和实测结果选择。

这些数字告诉我们三级流水变快了。下一页再看时间线，确认这个收益是否对应我们预期的重叠改善。

## 第 17 页 从时间线验证三级流水

这一页把两级和三级流水的时间线放在一起。横向是时间，不同轨道对应计算或搬运引擎；有颜色的条带代表活动区间，空白通常代表这条管线上没有执行相应工作。

左边是两级，耗时 346.7 微秒；右边是三级，耗时 287.9 微秒。这组对比固定了硬件、batch 和计算逻辑，主要改变的是流水深度。

看右边，Cube 的活动更密集，Vector 之间的一些空隙也缩短了。它支持的解释是：计算和数据准备重叠得更好，等待时间减少了；不能据此说某条矩阵乘指令本身变快了。

时间线的价值就在这里。只有总耗时，我们知道结果变快；结合各管线的活动位置，我们才能更有把握地解释为什么变快。

下面再把优化后的单核执行记录拆开，看看各个引擎的活动比例，同时说明这些百分比应该怎么读。

## 第 18 页 理解最终单核 trace

这页进一步展示长序列的单核 trace。trace 是一份带时间信息的执行事件记录。这个采样窗口的墙钟时间约 289.8 微秒，也就是从开始到结束实际经过的时间。

两路 AIV 的 Vector 都接近 96% 的忙碌比例，说明在这个采样中向量执行比较连续；Cube 和搬运管线也有较多重叠活动。

为什么这些百分比加起来会超过百分之百？因为不同引擎可以同时工作。比如在同一段时间里，Vector 正在计算，搬运引擎也可以传输数据，两者都会记为忙碌。这不是一张互斥的耗时饼图。

表中的事件数也不是指令条数。一个 Vector 事件可以包含很多条指令。

另外，这里的 289.8 微秒来自这次 trace，后面汇总的 287.5 微秒来自性能测试统计。这是两次不同口径的记录：一个用于分析执行过程，一个用于比较性能，不把它们当成同一次测量。

大序列的流水已经明显改善，但短序列还能不能再往前走一步？最后一项优化，针对的是编译器的调度估计。

## 第 19 页 用 latency hint 改善调度估计

最后一项优化是 latency hint，也就是给编译器一个计算成本提示。

编译器安排流水时，需要估计一段计算大概要花多少时间。如果估计与实际开销差距较大，安排出来的重叠关系就可能不理想。这里根据普通 softmax 大约 1344 条 SIMD 指令和参考吞吐，给出约 948 个周期的估计，再通过 T.SimdVF 的 latency 参数传给调度器。

948 是供调度使用的估计值，不是让程序主动等待 948 个周期，也不是一份新的实测延迟。softmax 的指令主体和数学计算没有因为这个提示而改变。

短序列的中位耗时从 13.3 降到 12.1 微秒，四轮独立测试对应约 9.0% 的时延下降。中长序列没有显示出同样明确的新收益。

长序列的最终记录还有 287.9 到 287.5 微秒的差值，但只有 0.4 微秒，仅凭这个差值不能判断它是稳定收益。因此，这一步主要看短序列从 13.3 到 12.1 微秒的变化。

到这里，几轮改动都介绍完了。下面把原始实现、每轮结果和最终结果放在一起，看累计收益。

## 第 20 页 累计性能结果

把全过程放在一起看，原始耗时是 33.2、469.2 和 2514.7 微秒，最终是 12.1、89.5 和 287.5 微秒，累计加速分别约为 2.74 倍、5.24 倍和 8.75 倍。

第一轮主要减少重复索引和概率布局转换；第二轮提高块间重叠；最后通过计算成本提示改善短序列调度。不同规模的场景，收益来源和幅度并不相同。

下面的图把原始耗时归一化为 100。最终剩余耗时约为原来的 36.4%、19.1% 和 11.4%。这些柱子的数值表示“还剩多少耗时”，不是“提升了多少倍”。

累计加速用原始耗时除以最终耗时来算，不能把每一轮的百分比直接相加。这里也再次说明，这是单算子结果。整个 DeepSeek-OCR 的加速，还取决于这个算子在模型总耗时中占多大比例，以及其他环节是否变化，不能直接套用 8.75 倍。

结果讲完以后，最后一部分我们回到诊断方法：今后看到类似性能现象，怎样更快地找到可以优化的位置？

## 第 21 页 进入结果复盘

下面进入第三部分。我们把前面的改动抽象成诊断方法，重点讨论如何从性能现象找到更具体、可以验证的问题。

## 第 22 页 从现象到证据

第一类现象是向量忙碌，但总耗时仍然高。前面已经看到，它可能对应大量重复工作。因此，要结合生成代码的指令数量和依赖关系，区分有效计算与可消除开销。

第二类现象是某个搬运引擎看起来很忙，实际带宽却不高。这里中等序列的例子同时出现较高的 MTE2 活动比例、较低的带宽利用，以及平均约 0.41 KB 的小传输。这组证据更值得检查小块搬运、访问步长和访问组织，而不是直接认定外部带宽已经跑满。表里这些指标的并列，是联合诊断线索，不是一条把百分比相乘的性能公式。

第三类是任务不均衡。短序列里，快任务和慢任务可以分别只有约 7.5 和 13.4 微秒。当任务需要全部结束后才能返回，最后完成的任务会拖长整体时间。这里的单任务 trace 和前面的性能中位数口径不同，不把两个数字直接等同。

还有一个容易误读的指标：两路 AIV 的忙碌比例相加可以超过 100%，例如表中的 152%。这表示两路并行活动的累计比例，不是一个核突破了百分之百利用率，也不能替代对时间线重叠关系的检查。

所以，性能分析不是看到一个高比例，就马上认定那里需要优化。我们先用指标找到值得检查的方向，再结合生成代码、传输粒度和时间线，把原因落实到具体操作。

最后，我把这次用到的方法归纳一下，方便大家在其他算子上尝试。

## 第 23 页 可复用的四种优化方法

最后总结四个方法。

第一，按依赖关系外提重复计算。key 的坐标不随 query 行改变，就不要放在 query 循环里反复求。

第二，让生产者直接输出消费者需要的布局。softmax 直接产出 NZ 概率块，避免先写普通布局再整理。

第三，按 shape 选择流水和实现。短序列与长序列的块数不同，额外缓冲和两遍处理的成本也不同，要用实测决定，而不是只保留一套参数。

第四，必要时校准调度器的成本估计。指令代码不变，合理的 latency hint 也可能改善执行安排，但需要重复测试确认，不把估计值当成事实。

应用这些方法时，正确性仍然是前提。我们要检查数值误差、尾块处理、掩码、缓冲复用和同步依赖。性能结果回答的是“有多快”，不能代替正确性验证。

## 第 24 页 结束与交流

今天的核心结论是：这个算子的优化，要同时理解计算依赖、数据布局和 Cube 与 Vector 的交接关系。我们通过减少重复工作和改善块间重叠，在三个测试场景上获得了明显的单算子收益。

如果只记住一个检查顺序，我建议是：先看这段计算依赖什么，再看它把数据写成了什么布局，最后看这些数据在不同执行单元之间有没有等待。

## 交流环节可直接使用的回答

### Patch embedding 和这个算子是什么关系

Patch embedding 先把图像区域变成向量序列；后续 ViT block 对序列继续编码。这个算子用于其中的注意力计算，让不同位置交换信息。它不负责切图，也不负责把像素映射成最初的向量。

### 为什么视觉注意力还需要位置信息

内容相似不代表空间位置相同。对于文档图像，上下和左右关系可能有不同意义。这里通过 REL_H 和 REL_W 给注意力分数加入二维空间关系。它与模型输入阶段可能使用的位置表示不是必须互相替代的同一个步骤。

### 为什么不直接一次生成完整注意力矩阵

完整分数和概率矩阵随序列长度平方增长，容易造成大量中间存储和读写。分块方法在片上逐块完成计算，并维护整行归一化状态，减少完整中间矩阵的落地和搬运。

### compact 实现会不会降低精度

这里 compact 主要描述布局和处理组织，并不是新增一种有损压缩。两条路径的概率都使用 BF16。不过，数据类型转换、浮点运算顺序和同步修改仍然需要正确性验证，不能仅凭名称宣称结果逐位相同。

### 为什么长序列的加速更明显

长序列有更多 key 块，原来的重复索引和布局整理执行次数更多，流水也有更多可重叠工作。短序列块数少，启动、收尾和任务均衡等开销占比更高，所以同一优化不一定获得相同倍数。

### 能不能统一使用三级流水

不一定。更深的流水需要更多缓冲和依赖管理，块数少时不容易覆盖额外成本。这次选择按 key 块数分派，阈值来自当前设备和测试场景，应在其他 shape 上重新验证。

### 这些结果能直接迁移到其他模型和设备吗

可以复用依赖分析、生产者布局和时间线诊断的方法，但不能直接照搬 13 个块的阈值、948 个周期的提示或具体加速倍数。硬件、编译器、shape 和数据类型变化后，应重新检查生成代码并测量。

### 整个模型能不能也加速 8 点 75 倍

不能从单算子结果直接推出。举例来说，假设这个算子原本占模型耗时的一半，另一半完全不变。算子加速 8.75 倍以后，整体还需要原来约 56% 的时间，所以整个模型只加速约 1.79 倍。因为没有改动的那一半耗时还在。这只是解释计算关系的例子，不代表本模型的实际耗时占比。
