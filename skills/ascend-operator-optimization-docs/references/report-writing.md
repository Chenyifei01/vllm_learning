# Ascend 算子优化报告写作指南

## 目标

报告应让读者能回答：算子为何重要、优化了哪条真实路径、瓶颈证据是什么、每个改动改变了什么、性能是否可信、正确性有没有覆盖，以及结论在哪些设备和 shape 上成立。

先检查仓库中的 `AGENTS.md`、算子代码、测试、基准脚本、profiler 输出和已有报告模板。用户提供的模板和术语优先。仓库里的旧报告可作风格参考，但其中的指标和结论只对原实验成立。

## 推荐叙事结构

根据材料裁剪，不要求机械套用全部标题：

1. **结论摘要**：目标路径、核心瓶颈、主要改动、关键收益、正确性状态、剩余限制。
2. **算子与场景**：算子语义、输入输出、模型调用位置、生产 shape、dtype、变体分发条件。
3. **环境和测量口径**：硬件与软件版本、测试 shape、基线版本、计时方法、预热/重复次数、统计量、噪声控制。
4. **基线画像**：端到端延迟、吞吐/带宽、算子级时间、关键 pipe/资源计数器。解释这些数如何支持瓶颈判断。
5. **逐轮优化记录**：每轮按“假设 → 改动 → 预期信号 → 验证 → 结果 → 结论”叙述。成功、无收益和回退都保留。
6. **正确性与边界**：确认的测试结果、覆盖范围、边界 shape、数值范围、异常参数和已知限制；需要审计或用户要求时再展开 golden、误差度量和断言细节。
7. **最终结果**：相同口径下的基线/各轮/最终对比；明确适用 dtype、shape、设备及收益的绝对值和百分比。
8. **结论与适用范围**：最终瓶颈、可复用经验、不能外推的条件；复现入口仅在交付允许且读者可访问时添加。

若报告面向快速评审，摘要和最终结果前置；若面向技术复盘，保留逐轮证据和负结果。

## 独立交付与本仓库偏好

- 对外单文件报告应能独立读懂。借鉴其他优化的机制要在本报告内解释，不使用“姊妹战役”“另有报告”或只有作者理解的内部背景作为论据。
- 不默认添加附录、私仓源码定位表、分支/commit 和外部测试脚本链接。用户要求复现且访问条件满足时可以加入；否则将必要的环境、计时口径和算法说明保留在正文。
- 精度结果按用户要求简要写“精度测试通过”，有证据时可补用例数、覆盖范围和未覆盖项。报告不需要详细断言，不意味着可以跳过核验测试日志或改变测试断言。
- 不为验证措辞改算子实现、基准脚本或测试。无法确认是否通过时标“待确认”，不能从历史版本的通过结果推断当前版本也通过。
- Markdown 是事实源；若同时交付 HTML/PDF，导出同一份确认后的正文，不在某个格式中另加私仓引用或被删除的附录。格式细节见 [document-export.md](document-export.md)。

## 性能证据

- 优先先确定实际命中的 tiling/key/dispatch，再决定优化对象。静态推测和任务简报不代替运行时证据。
- 每个指标写明单位、统计口径、shape、dtype、设备、对照版本和采集来源。区分 kernel wall time、端到端时间、pipe busy 时间、吞吐和带宽。
- 明确计数器是否重叠。多个 pipe 的忙碌时间可能并行，不能当作互斥时间直接相加。
- 写百分比时核实分母：`pipe busy / kernel wall` 与“各核活跃时间占比的均值”不是同一口径。不同采集点或 profiler 模式的指标不拼成一份时间分解。
- 性能对比保持测试设置一致；报告重复次数、聚合方式（中位数/分位数等）和波动区间。小 shape 同时写绝对变化，避免百分比放大噪声。
- 有条件时做 A/B 交错测量，并用未改路径或已知稳定基准估算设备噪声。明确区分“超过噪声带”与“方向看似改善”。
- 噪声对照按同设备、同 shape、同轮设置解释；不以一个小 shape 的百分比波动裁定另一个大 shape 的收益。未经独立复测，不将未改路径的波动认领为优化收益。
- 吞吐或带宽数字给出分子、分母、字节单位（MB/MiB、GB/s/GiB/s）和公式。Roofline 下限与峰值来源写清。
- 统一收益符号与基线：“时延变化”可用 `(新值−基线)/基线`，负值更快；“提升率”可用 `(基线−新值)/基线`，正值更快。累计收益用最终值对原基线复算，不把各轮百分比相加。有效带宽接近峰值或墙钟接近理论下限，不等于已证明剩余差值都能兑现为收益。
- 不把预测、静态分析和设备实测混写。用“假设/预期”标注未验证内容，用设备日志/trace/测试结果支撑结论。
- 分发和 pass/UB 计数表注明是基线、中间轮次还是最终状态。后续正确性修复回退了变换时，摘要和终值表同步更新；保留中间读数时明确标“历史结果”。

## 每轮记录模板

```text
假设：哪项成本主导，证据是什么？
改动：具体修改了哪条变体/路径，语义保持条件是什么？
预期：哪些计数器、指令数、流水重叠或时延应发生变化？
结果：对应 shape、dtype、重复统计和正确性结果。
判定：收益、噪声级、回退或负结果；解释与假设是否一致。
```

不要删除失败实验：写出变量、控制条件、观察和最终决定。它们能防止团队重复付出并限制后续外推。

## 正确性与 AscendC 特有关注点

- 在优化前写清算子契约：运算顺序、舍入/累加精度、输出别名、mask/tail 行为、epsilon 与可选输入语义。
- 将结果容差与契约对应。先核验测试使用的比较方式和容差依据；仅在用户要求精度审计或详细复现时，在报告展开绝对/相对误差、ULP 或位级比较。
- 覆盖生产路径和回退路径、不同 dtype/变体、尾块、tile/UB 边界、极小/极大数值、无可选参数及非法参数。
- 对双缓冲和事件同步，说明槽位索引、发射/消费守卫、事件生命周期和退出时的在途操作；以死锁/越界/NaN 检查支撑安全结论。
- UB 预算列出各缓冲区的数量、dtype、对齐、固定开销、总占用和余量，并注明 tiling 选择与回退阈值。
- 数学等价不等于数值契约等价；缩放前后移动等改动需核验舍入和溢出域。说明正确性修复的性能代价及回退范围，不能把理论收益当作最终收益。
- 芯片实测行为注明型号、CANN/编译器和适用范围。不要把 c220 或某一 CANN 版本的现象直接推广到其他代际。

## 图表与引用

- 图表应回答一个明确问题，显示对照关系、单位和关键 shape；图下注明测量口径或数据来源。
- 时延曲线跨越多个数量级时选择 log 轴、拆成小图，或把 decode/prefill 分开。不要让关键小值挤在坐标轴底部。
- 图例颜色、系列名称和表格版本命名保持一致。图中的收益百分比与正文表格重新核算。
- 仓库内 Markdown 图片使用相对路径，逐个确认链接存在，并将 SVG/PNG 实际渲染检查；XML 可解析不等于图可读。单文件交付不依赖这些路径，按导出指南将资源内嵌。
- 不假定目标 Markdown 查看器支持内联 SVG、HTML 或 data URI；需要单文件且尚未验证查看器支持时，优先提供自包含 HTML/PDF。只在导出页中增加图号/图注，不改变图中测量值。
- 流水图标清是机制示意还是实测 trace。双缓冲示意须表达同槽位复用前等待消费者完成的依赖，不把两槽画成可无限提前装载。
- 所有图片加简明替代文本。图中字体、字号、背景和对比度应适配目标查看器。

## 出稿核对

- [ ] 摘要中的主结论在正文有对应证据。
- [ ] 变体、版本、shape 和结果能一一对应，未把未修改路径的收益记在改动名下。
- [ ] 计算公式、单位、百分比和累计收益可复算。
- [ ] 正确性数据与性能数据来自明确的版本和测试口径。
- [ ] 缺失数据标为“未测/待补”，没有根据常识补造具体值。
- [ ] 图表、相对路径、表格和代码片段显示正常。
- [ ] 已注明测试限制、噪声、回退路径和结论适用范围。
- [ ] 独立交付没有要求读者访问私仓或下载未随文提供的附件；HTML/PDF 与确认正文一致。
